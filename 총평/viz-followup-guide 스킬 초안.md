# viz-followup-guide 스킬 초안

## 상태

정식 스킬이 아닌 초안이다. 아래 세 가이드에서 공통 형식을 뽑아 정리했다.

- `[58기-데타출동] 261105ㅣ프로젝트 평가 및 후속 분석 가이드.md`: 후속 분석 갈래, 데이터 있음
- `[58기-마이쭈] 261106ㅣ프로젝트 평가 및 후속 분석 가이드.md`: 주제 재선정 갈래
- `[58기-모래시계] 261106ㅣ프로젝트 평가 및 후속 분석 가이드.md`: 후속 분석 갈래, 보고서만 있고 분석 단위를 바꿈

## 용도

시각화 프로젝트(예측 모델 없이 기술통계와 그래프로 인사이트를 낸 프로젝트)가 끝난 팀에게, 다음 단원인 회귀분석·머신러닝으로 무엇을 이어 갈지 안내하는 슬라이드 원고를 만든다.

이 스킬은 페이지별 첨삭을 하지 않는다. 첨삭은 `viz-project-feedback`이 맡는다. 여기서는 프로젝트 전체를 한 번 평가하고 다음 방향을 정하는 데 집중한다.

## 작성 전 확인

아래 항목이 요청에 없으면 작성 전에 사용자에게 묻는다.

### 검토 대상

팀의 최종 분석 보고서 파일이다. 같은 폴더의 html·pdf 빌드 산출물은 검토 대상이 아니다.

### 원본 데이터·노트북 유무

있으면 수치와 변수 후보를 데이터에서 직접 확인한다. 없으면 보고서만 근거로 쓰고, 표지의 "읽기 전에" 상자 첫 문장에 그 사실을 밝힌다(고정 문구 참고).

### 작성자·날짜

표지의 `author`와 `date`다. 기존 가이드는 `ITWILL 주영아 강사`를 썼다.

## 작업 순서

### 1. 보고서 읽기

- `pdftotext -layout`으로 전체 글을 뽑는다.
- 그래프가 핵심인 쪽(데이터 수집 표, 대표 그래프, 지도·히트맵)은 `pdftoppm -r 60`으로 이미지를 만들어 직접 본다. 이미지는 스크래치 폴더에 둔다.
- 팀의 핵심 질문(Q1, Q2 …), 각 질문의 결론, 팀이 스스로 적은 한계를 정리한다.

### 2. 수치 검산

- 보고서의 표 값으로 합계·평균·중앙값·비율을 다시 계산한다.
- 같은 수치가 여러 쪽에 나오면 서로 맞는지 대조한다.
- 다른 행과 동떨어진 값(예: 한 구만 지나치게 적은 시설물 수)과 등록 기준이 달라 보이는 값(예: 카메라 대수 = 설치 개소 수)을 찾는다.
- 찾은 문제 가운데 후속 분석 결과를 흔들 수 있는 것만 "보완 사항"에 넣는다. 오탈자 수준의 문제는 가이드에 넣지 않고 사용자에게만 보고한다.

### 3. 발전 가능성 판정

아래 다섯 기준으로 지금 데이터가 회귀분석으로 이어질 수 있는지 판정한다.

| 기준 | 갖춘 상태 |
| --- | --- |
| 분석 단위 | 한 행이 사람·상품·거래 하나인 개별 단위 데이터 |
| 행 수 | 수천 개 이상 |
| 종속변수 | 연속형 숫자 |
| 요인 후보 | 5개 이상이 한 표에 함께 있음 |
| 질문 | 결과를 미리 단정할 수 없음 |

판정 결과에 따라 세 갈래 중 하나로 간다.

- **갈래 A. 그대로 후속 분석:** 지금 데이터가 기준을 대부분 갖췄다(데타출동).
- **갈래 B. 단위를 바꿔 후속 분석:** 지금 데이터는 집계값이지만, 같은 주제에서 개별 단위 원자료를 구해 지금 데이터를 특성으로 붙일 수 있다(모래시계: 서울서베이 원자료 + 자치구 특성).
- **갈래 C. 주제 재선정:** 같은 주제로는 개별 단위 원자료도 구하기 어렵고 변수가 너무 적다(마이쭈).

갈래 B에서 원자료를 제안할 때는 출처가 실제로 있는지 검색으로 확인한다. 필요한 문항·키가 원자료에 들어 있는지 확인하지 못했으면 "분석 조건"에 먼저 확인할 일로 적는다.

### 4. 원고 작성

아래 쪽 구성과 문장 규칙에 따라 원고를 쓴다.

### 5. 빌드 확인(선택)

`node_modules`가 있으면 `npx slidev export`로 빌드해 쪽 넘침을 확인한다. 없으면 빌드하지 않았다고 보고한다.

## 쪽 구성

### 갈래 A·B

| 순서 | 제목 | 레이아웃·컴포넌트 | 내용 |
| --- | --- | --- | --- |
| 1 | 표지 | `cover` | 제목, 보고서 주제, "읽기 전에" 상자 |
| 2 | 총평 | `Review` | 잘된 점 4개, 한계 2~3개, 아래 띠 한 줄 |
| 3 | 근거 점검 | `Checklist` 또는 `Bars` | 팀 결론의 근거가 얼마나 얇은지, 요인끼리 함께 움직이는지 수치로 보임 |
| 4 | 후속 분석 방향 | `Flow` | 출발점 → 필요한 결론 → 필요한 분석, 검토 범위 한계 상자 |
| 5 | 데이터 결합 | 표 | 갈래 B에서만 넣음. 단위·데이터·출처·쓰임, 결합 키 |
| 6 | 변수 설계 | 표 | 구분·변수·유형·내용 |
| 7 | 가설 설계 | `Hypo` | 요인 4개 안팎, 팀의 Q와 연결 |
| 8 | 보완 사항 | `Stats` | 큰 숫자 4칸 |
| 9 | 분석 조건 | `blocks` | 조건 1~3 |
| 10 | 해석 범위 | `CanCannot` | 분석 조건에 해석 범위를 넣었으면 생략 |

### 갈래 C

| 순서 | 제목 | 레이아웃·컴포넌트 | 내용 |
| --- | --- | --- | --- |
| 1 | 표지 | `cover` | 제목은 "시각화 프로젝트 총평과 주제 재선정 방향" |
| 2 | 총평 | `Review` | 아래 띠에 "시각화로는 훌륭하지만 회귀분석으로 발전시키기에는 변수가 제한적"이라는 판정 |
| 3 | 발전 가능성 판정 | `Checklist` | 요인 후보·예상된 결과·관측값 수·목표 변수 |
| 4 | 주제 재선정 기준 | `CanCannot` | 다음 주제에 필요한 것 ↔ 지금 주제의 상태, 예시 데이터 |

## 테마 컴포넌트

`slidev-themes/editorial/components`의 컴포넌트다. props는 원본 vue 파일의 주석을 따른다.

### Review

`good: string[]`, `limits: {text, sub?}[]`, `foot?`. `sub`에는 비유를 한 줄 넣는다.

### Checklist

`rows: {label, value, unit?, text}[]`. 값 하나로 판정 근거를 보일 때 쓴다.

### Bars

`items: {label, value}[]`, `title`, `note`. 두 요인이 함께 움직이는 모습을 보일 때 쓴다. `note`에 보고서 쪽 번호를 적는다.

### Flow

`steps: {kicker, title, text}[]`. kicker는 `출발점`·`필요한 결론`·`필요한 분석`으로 고정한다.

### Hypo

`items: {label, tag, h0, h1, note?}[]`. `tag`에 팀의 질문 번호(Q1 등)를 적는다.

### Stats

`items: {label, value, unit, text}[]`. 4칸을 기본으로 한다.

### CanCannot

`can`, `cannot`, `notes`, `canLabel?`, `cannotLabel?`. 해석 범위와 주제 재선정 비교에 함께 쓴다.

## 고정 문구

### 읽기 전에(데이터 없음)

> 이 자료는 원본 데이터와 노트북을 받아 보지 못한 채, 제출된 분석 보고서만 근거로 작성했습니다. 실제 데이터를 열어 분석하는 과정에서 변수, 결합 방법, 분석 방법은 얼마든지 달라질 수 있습니다.

### 읽기 전에(진도)

> 이 자료에는 아직 배우지 않은 회귀분석 내용이 들어 있어, 지금은 이해하기 어려운 부분이 있을 수 있습니다. 앞으로의 진도를 익힌 뒤 후속 분석에 참고하기 바랍니다.

데이터가 없으면 두 문단을 모두 넣고, 데이터 없음 문단을 먼저 쓴다.

### 검토 범위의 한계

> 이 방향은 [시각화 프로젝트의 결과를 바탕으로 데이터를 대략적으로만 검토해 / 원본 데이터 없이 보고서만 보고] 도출한 것입니다. 데이터를 자세히 살펴보면 변수와 분석 방법은 충분히 바뀔 수 있습니다.

## 문장 규칙

### 독자

수강생이 읽는다. 고등학생에게 설명할 수 있는 말로 쓰고, 전문 용어는 처음 나올 때 한 번 풀어 쓴다.

### 근거

수치에는 보고서 쪽 번호를 붙인다(예: `p.15`). 계산한 값은 보고서 표에서 다시 계산할 수 있어야 한다.

### 비유

총평의 핵심 한계 하나에만 일상 비유를 한 줄 붙인다(비싼 식당과 코스 요리, 군고구마와 감기, 학교 크기와 지각생).

### 가설

"다른 요인이 같으면 ~은 같다" / "다른 요인이 같아도 ~에 따라 다르다"의 짝으로 쓴다. 팀의 예상이나 결론을 가설로 다시 확인할 수 있으면 `note`에 밝힌다.

### 해석 범위

관찰 데이터라서 "경향"까지만 말할 수 있다고 쓴다. 말할 수 있는 문장과 말할 수 없는 문장을 하나씩 짝지어 보이고, 역인과(결과가 원인을 부르는 경우) 가능성이 있으면 반드시 적는다.

### 제목

쪽 제목은 `총평`, `변수 설계`, `조건 1. 데이터 보완`처럼 짧은 단어형으로 쓴다. 의문문 제목은 쓰지 않는다. 결론은 제목이 아니라 본문 첫 문장에 쓴다.

### 칭찬

잘된 점은 팀이 실제로 한 행동을 구체적으로 적는다(무엇을 확인했고 어떻게 처리했는지). "꼼꼼했다" 같은 평가어만 쓰지 않는다.

## 파일 규칙

### 이름

`[기수-팀명] YYMMDDㅣ프로젝트 평가 및 후속 분석 가이드.md`로 저장하고, 보고서와 같은 폴더에 둔다.

### 머리말

```yaml
---
theme: ./slidev-themes/editorial
addons:
  - slidev-addon-studio
title: 시각화 프로젝트 총평과 후속 분석 방향
sidebar: true
fontScale: 1
colorMode: light
exportDark: false
layout: cover
eyebrow: 팀명 · 시각화 프로젝트 지도
author: ITWILL 주영아 강사
date: YYYY.MM.DD
---
```

## 마치고 보고할 것

- 판정한 갈래와 그 근거
- 확인하지 못한 전제(예: 원자료에 필요한 문항이 있는지)
- 가이드에 넣지 않은 수치 문제
- 빌드 여부

## 미정 사항

- 작성 전 확인을 다른 피드백 스킬처럼 질문 카드(AskUserQuestion)로 할지
- 쪽 넘침 검사를 `slidev-deck`의 `check_overflow.py`로 할지
- 머신러닝(분류) 갈래를 따로 둘지. 지금 세 가이드는 모두 선형회귀만 다룬다.
